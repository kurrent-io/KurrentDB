# Testing

> [TUnit](https://tunit.dev/) on Microsoft.Testing.Platform — not VSTest. `global.json` configures MTP
> directly. All TUnit CLI flags go after `--`.

## Overview

**CI gating**: unit tests run on every PR; integration tests run on all non-draft PRs and on direct pushes to `main`.

- TUnit attributes only (`[Test]`, `[Arguments]`, `[Category]`); no xUnit/NUnit attributes
- Aspire for test containers (`test/Aspire.Hosting.KurrentDB`)
- `Assert.That(...)` exclusively — Shouldly is not in this project

## Running Tests

Always use the test runner — never invoke `dotnet test` directly. Do not add, remove, or
modify flags; the runner already includes the correct invocation. Only change the category (`unit`, `integration`, or `all`) and
the `--treenode-filter`.

The runner is a C# file-based app (`scripts/testing/test-runner.cs`) using Spectre.Console for live
status output, CliWrap for process management, and System.CommandLine for argument parsing:

```
dotnet scripts/testing/test-runner.cs -- <action> <category> [args...]
```

```sh
dotnet scripts/testing/test-runner.cs -- run unit                                       # all unit tests
dotnet scripts/testing/test-runner.cs -- run integration                                # all integration tests
dotnet scripts/testing/test-runner.cs -- run all                                        # unit + integration combined
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/ReadTests/*"  # specific class
dotnet scripts/testing/test-runner.cs -- run unit --run-id 7f3a9c2e1b                   # fixed UNIQUE results folder (use a GUID)
dotnet scripts/testing/test-runner.cs -- list unit                                      # list without running
```

To scope a run to a single test project (assembly), use the first segment of the treenode filter:

```sh
dotnet scripts/testing/test-runner.cs -- run all --treenode-filter "/Kurrent.Client.Tests/*/*/*"    # all client tests
dotnet scripts/testing/test-runner.cs -- run all --treenode-filter "/Kurrent.Streaming.Tests/*/*/*" # all streaming tests
```

The runner enforces the category filter automatically, creates a unique results folder per run, and
shows live status with failures + summary. Extra TUnit args pass through verbatim after the category:

```sh
dotnet scripts/testing/test-runner.cs -- run integration --fail-fast --timeout 60s
dotnet scripts/testing/test-runner.cs -- run integration --maximum-parallel-tests 1
```

The runner builds once (`dotnet build -c Release`) then runs the tests with `--no-build`. Pass `--rebuild`
to force that build to `--no-incremental` — only needed when you want the trim/AOT analyzers to re-emit
warnings (an up-to-date incremental build skips compilation), not for normal test runs.

### Results

Each run writes to `.artifacts/test-results/<run-id>/`. The `<run-id>` is auto-generated unless you pass
`--run-id <guid>` — a **unique** value (a GUID), which fixes the folder name so you know the path before the
run even finishes. Reusing a value writes into the same folder and mixes reports, so always generate a fresh one:

* `*.trx` — one TRX file per test assembly, named `{assembly}-{os}-{tfm}-report.trx`
* `*.md` — one markdown report per assembly, generated by `trx2md.py` (same name, `.md` extension)
* `*.html` — one HTML report per assembly, generated by TUnit (only when `--html-report` is passed)
* `output.log` — raw dotnet test output, last resort for runner/infrastructure issues or deep investigation when
  normal diagnostics fail

Generate the `<run-id>` from a real entropy source — never hand-fabricate a GUID, which risks collisions and
non-uniqueness:

```sh
uuidgen | tr 'A-Z' 'a-z' | tr -d '-'   # primary; normalizes macOS uuidgen (uppercase + dashed) to 32 lowercase hex
openssl rand -hex 16                    # fallback when uuidgen is unavailable; already 32 lowercase hex, no dashes
```

Never delete `.artifacts/test-results/`. **Pass a unique `--run-id <guid>` so the results path is deterministic**,
then read `.artifacts/test-results/<guid>/*.md` directly. Never scrape the background-task `.output` file or the
console to discover the generated folder name — that is pure overhead. Always use the `.md` report files to
check test outcomes. Do NOT parse `output.log` or background task stdout for results.

### Tool call invocation

Tests are the verification step, not `dotnet build`. The runner builds once (`dotnet build -c Release`)
then runs tests with `--no-build`, so a standalone `dotnet build` beforehand is redundant. After any code
change (moves, refactors, edits, new code), run the relevant tests as the single verification step before
reporting done.

When running tests via the Bash tool:

- **Always background**: `run_in_background: true`.
- **Use the runner**: `dotnet scripts/testing/test-runner.cs -- run unit` (or `integration`).
- **Timeouts based on observed execution time, not guessed defaults.** Memory holds
  observed averages from successful runs. Reference them before running a scope.
  - **If memory has an observed time for this scope**: set Bash `timeout` to
    `max(observed × 1.5, observed + 30s)`.
  - **If no observed time recorded**: use a conservative initial value — 60s for
    a single test or small filtered subset, 3 min for a full suite. After the
    first successful run, record the actual duration in memory.
  - **If observed times drift** (current run takes more than 2× the recorded
    value, or hits the timeout): update the memory entry with the new average
    and investigate why it slowed.
- **Polling**: use `TaskOutput` with `block: false`. Never re-block on a
  backgrounded task; either continue with other work or wait for the task
  notification.
- **Pass a unique `--run-id <guid>`** (generate a fresh GUID per run) so the results
  folder is known up front (`.artifacts/test-results/<guid>/`). After the task
  completes, read its `*.md` reports directly — do NOT open the background-task
  `.output` file or scrape the console to find the folder. Each assembly produces its
  own `{assembly}-{os}-{tfm}-report.md`.

Note: `--timeout 60s` (TUnit flag) bounds individual tests; the Bash `timeout`
parameter bounds the whole invocation. Different scopes — set both.

TRIPWIRE 1: About to report test results. Are you reading `.md` report files from
the run's results folder (`.artifacts/test-results/<run-id>/*.md`)? If you are
reading the background task stdout file or `output.log` — stop. Read the `.md` reports.

TRIPWIRE 2: About to start a new test run. Are there background test tasks still
running from earlier in this session? Stop them first — stale runs waste resources
and can cause port/container conflicts.

TRIPWIRE 3: About to invoke the test runner. Is your working directory the repo
root? If not, use the absolute path. The C# runner needs `dotnet run` to resolve
the script path relative to the working directory.

TRIPWIRE 4: About to invoke `dotnet test` directly, or pass `--project`,
`--framework`, or a path-based project selector. Stop. Use the runner.

TRIPWIRE 5: About to run `dotnet build` to verify a code change. Stop. Run the
tests instead — the runner builds before testing. A green build only proves
compilation; tests prove correctness.

### Test Filtering

Tree-node filters (not VSTest `--filter`). Pattern: `/Assembly/Namespace/Class/Method[Property=Value]`.
Use `*` as wildcard. The script merges the category filter automatically.

```sh
dotnet scripts/testing/test-runner.cs -- run integration --treenode-filter "/*/*/AppendRecordsTests/creates_single_stream" # single test
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/ReadTests/*"                                     # by class
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/ReadTests/reads_events_from_stream"              # by method
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/*/*[Category=Streams]"                           # by category
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/(ClassA)|(ClassB)/*"                             # OR classes
dotnet scripts/testing/test-runner.cs -- run unit --treenode-filter "/*/*/*/*[(Category=Streams)&(Priority=High)]"         # AND props
```

OR (`|`) and AND (`&`) work within a single path segment only. One `[...]` group per segment.

## AOT Compatibility Report

`scripts/testing/aot-report.cs` generates an AOT/trim warnings report for the publishable packages. It
discovers every project marked `<IsAotCompatible>true</IsAotCompatible>`, builds each with
`--no-incremental` so the trim/AOT analyzers re-run from scratch, and writes a markdown report grouped by
project to `.artifacts/aot-report.md`.

```sh
dotnet scripts/testing/aot-report.cs               # -> .artifacts/aot-report.md
dotnet scripts/testing/aot-report.cs -- --stdout   # print to stdout instead of writing
```

Warnings split into **own code** (actionable `IL2026`/`IL3050`/`IL2070`/…) and **packages** (`IL3058` —
dependencies not marked AOT-compatible, listed with versions). AOT/trim warnings only surface on a
non-incremental build — the same reason the test runner exposes `--rebuild`.

## Skipping Tests

### SkipAllAttribute

Assembly-level attribute for centralized skip management. Apply multiple instances to create a skip registry:

```csharp
// Skip all tests in a specific class
[assembly: SkipAll(typeof(StreamReadTests), "Blocked by DEV-1234")]

// Skip all tests under a namespace prefix
[assembly: SkipAll("Kurrent.Client.Tests.Integration.Streams", "Server upgrade in progress")]
```

Place `[Skip("reason")]` on individual `[Test]` methods only. For anything broader — an entire class,
multiple classes, or a namespace — use `[assembly: SkipAll(...)]` in the test project's
`TestkitBootstrap.cs`. This keeps skip decisions centralized and auditable in one file instead of
scattered across test classes.

TRIPWIRE: About to add `[Skip]` to a class declaration, or add `[Skip]` to every test method in a
class. Stop. Use `[assembly: SkipAll(typeof(TheClass), "reason")]` or
`[assembly: SkipAll("Namespace.Prefix", "reason")]` in `TestkitBootstrap.cs` instead.

## Test Infrastructure

### Testkit Harness

All runnable test projects wire up the testkit:

```csharp
[assembly: TUnit.Core.Executors.TestExecutor<TestkitTestExecutor>]
```

Provides: per-test GUID injection and OTel metadata, scoped Serilog logger per test, `RpcException`
translation into human-readable failures, automatic container lifecycle management.

### Property Injection

TUnit uses AOT-compatible property injection with `required` properties:

```csharp
public class MyTests {
    [ClassDataSource<KurrentDBFixture>(Shared = SharedType.PerTestSession)]
    public required KurrentDBFixture Fixture { get; init; }
}
```

Sharing modes: `PerTestSession` (single instance), `PerAssembly` (one per assembly), `PerClass` (one per class), `Keyed` (shared by key), *(none)* (new per test).

Objects implementing `IAsyncInitializer` initialize automatically. Objects implementing `IAsyncDisposable` dispose when their sharing scope ends.

Fixture variants: `KurrentDBFixture` (default, TLS), `KurrentDBInsecureFixture` (TLS off), `KurrentDBScavengeFixture` (session-scoped, ephemeral), `KurrentDBClusterFixture` (3 nodes + 1 replica).

### Project Structure

One test project per src project. Unit and integration tests live in the same project, split into
`Unit/` and `Integration/` top-level folders. Never propose separate `*.Integration.Tests`,
`*.E2E.Tests`, or `*.Functional.Tests` projects.

Integration tests use `[Category("Integration")]`. Tests without this attribute are treated as unit tests.

### Containers

Test containers are managed by Aspire (`test/Aspire.Hosting.KurrentDB`). Fixtures in `test/Kurrent.Sdk.Testkit/` wrap the Aspire app host.

- Container image configured via `appsettings.json` under `KurrentDB:ImageRef`
- CI overrides via env var: `KURRENTDB__IMAGEREF`
- TLS certificates generated automatically by the Aspire harness (`AddCertificateGenerator`)
- Supports insecure and secure (TLS) modes

### Observability

The Aspire test harness exports OpenTelemetry data automatically. Aspire Dashboard at http://localhost:18888.

### Assertions

`Assert.That(...)` is the only assertion style. All assertions are async and must be awaited.

```csharp
await Assert.That(value).IsEqualTo(expected);
await Assert.That(value).IsNotEqualTo(other);
await Assert.That(value).IsTrue();
await Assert.That(value).IsFalse();
await Assert.That(value).IsNull();
await Assert.That(value).IsNotNull();
await Assert.That(collection).Contains(item);
await Assert.That(collection).DoesNotContain(item);
await Assert.That(action).Throws<TException>();
await Assert.That(asyncAction).ThrowsAsync<TException>();
```

Chain with `.And` / `.Or`:

```csharp
await Assert.That(value).IsNotNull().And.IsEqualTo(expected);
await Assert.That(value).IsEqualTo(1).Or.IsEqualTo(2);
```

Use `.Within(tolerance)` for numeric and DateTime comparisons:

```csharp
await Assert.That(actual).IsEqualTo(expected).Within(TimeSpan.FromSeconds(1));
await Assert.That(actual).IsEqualTo(expected).Within(0.01);
```

### Data-Driven Test Attributes

- `[Arguments(...)]` — inline test data per test case
- `[MethodData(nameof(Method))]` — test data from a static method
- `[ClassDataSource<T>]` — class-based data sources with sharing modes (see Property Injection)

For integration tests, use `ITestDataSource` instead of hand-crafting data (see Conventions below).

## Execution Control

### Timeouts

`[Timeout(milliseconds)]` at method, class, or assembly level. Priority: method > class > assembly. Each `[Retry]` attempt gets its own fresh timeout.

Integration tests must always have a timeout — `[Timeout(10_000)]` on the class is usually enough. A test
that takes more than 10 seconds is already broken. The Bash tool `timeout` parameter is NOT the test timeout
— the test framework needs its own.

### Retries and Repeats

Avoid both unless there is a strong, documented reason. They are hacks that mask root causes.

```csharp
[Retry(3)]   // re-runs only on failure, stops when it passes
[Repeat(3)]  // always runs N additional times unconditionally
```

`[Retry]` is almost always wrong — a test that needs retries is a flaky test, and the correct fix is
to find and eliminate the flakiness, not hide it behind retries. `[Repeat]` has narrow legitimate uses
such as stress-testing to reproduce intermittent behavior, but not as a permanent fixture.

TRIPWIRE: About to add `[Retry]` or `[Repeat]` to a test. Can you explain why the test is flaky and
why fixing the root cause is not possible? If not, diagnose the flakiness instead of adding retries.

### Parallelism

TUnit runs all tests in parallel by default.

```csharp
[NotInParallel("key")]    // tests with same key never overlap
[ParallelGroup("Phase1")] // all tests in the group run together, isolated from other groups
[ParallelLimiter<T>]      // cap concurrency (T implements IParallelLimit)
```

Use `[NotInParallel]` when tests must not overlap with each other (shared resource). Use `[ParallelGroup]` when a set of tests should run in isolation from the rest of the suite but can still run in parallel with each other within the group.

CLI override: `-- --maximum-parallel-tests 4` (0 = unlimited).

### Ordering

Prefer `[DependsOn]` over `[NotInParallel(Order = N)]` — preserves parallelism for unrelated tests. Share state via `TestContext.Current!.StateBag`.

### Exit Codes

Returned by the test process after execution. `dotnet test` exits with code 0 if the test process exits with code 0,
even if tests failed.

| Exit code | Details                                                                                                                                                                                                                                                       |
|----------:|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|         0 | Indicates success. All tests that were chosen to run ran to completion and there were no errors.                                                                                                                                                              |
|         1 | Indicates unknown errors and acts as a catch all. To find additional error information and details, look in the output.                                                                                                                                       |
|         2 | An exit code of 2 is used to indicate that there was at least one test failure.                                                                                                                                                                               |
|         3 | Indicates that the test session was aborted. A session can be aborted using Ctrl+C, as an example.                                                                                                                                                            |
|         4 | Indicates that the setup of used extensions is invalid and the tests session cannot run.                                                                                                                                                                      |
|         5 | Indicates that the command-line arguments passed to the test app were invalid.                                                                                                                                                                                |
|         6 | (no longer used) Exit code 6 is no longer produced by the platform; it previously indicated that the test session was using a non-implemented feature.                                                                                                        |
|         7 | Indicates that a test session was unable to complete successfully, and likely crashed. It's possible that this was caused by a test session that was run via a test controller's extension point.                                                             |
|         8 | Indicates that the test session ran zero tests.                                                                                                                                                                                                               |
|         9 | Indicates that the minimum execution policy for the executed tests was violated.                                                                                                                                                                              |
|        10 | Indicates that the test adapter, Testing.Platform Test Framework, MSTest, NUnit, or xUnit, failed to run tests for an infrastructure reason unrelated to the test's self. An example is failing to create a fixture needed by tests.                          |
|        11 | Indicates that the test process will exit if dependent process exits.                                                                                                                                                                                         |
|        12 | Indicates that the test session was unable to run because the client does not support any of the supported protocol versions.                                                                                                                                 |
|        13 | Indicates that the test session was stopped due to reaching the specified number of maximum failed tests using --maximum-failed-tests command-line option. For more information, see the Options section in Microsoft.Testing.Platform CLI options reference. |

## Troubleshooting

**"no tests found"** — Verify `<IsTestProject>true</IsTestProject>`, TUnit is referenced, test methods have `[Test]` and are public instance methods, `.csproj` has `<OutputType>Exe</OutputType>`.

**Filter matches nothing** — Use `dotnet scripts/testing/test-runner.cs -- list unit` to see the tree structure. Category names are case-sensitive.

**Tests hang** — Check Docker logs. Use `--timeout 3m` and `--maximum-parallel-tests 1` to isolate.

**"gRPC Unimplemented"** — Server version mismatch. Pull latest image; remove stale containers.

## Conventions

1. **Test method names use `snake_case`** — e.g., `appends_record_to_new_stream`. Reads as a sentence describing the behavior.

2. **Test methods must return `ValueTask`, not `Task`.** All async test methods (`[Test]`) use `ValueTask` as the return type, never `Task`.

3. **Use Bogus Faker for test values, never hardcoded constants.** Generate test data via the `BogusFaker` class data source instead of inline literals. This avoids `TUnitAssertions0005` warnings naturally — don't suppress analyzer warnings to work around constant values.

   Add the fixture to every test class and use it for all test values:
   ```csharp
   [ClassDataSource<BogusFaker>(Shared = SharedType.PerTestSession)]
   public required BogusFaker Faker { get; [UsedImplicitly] init; }
   ```

4. **Arrange-Act-Assert rules:**

   * Add `// Arrange`, `// Act`, `// Assert` comments to every test. 
   * Pre-compute all expected values in Arrange. Never do calculations inside Assert — e.g. `simulation.Records.Count - 1` belongs in a `var expectedRevision` upfront, not inline in the assertion. 
   * Assert full objects when possible. Use `new StreamRevision(stream, revision)` and compare the whole struct instead of asserting `.Stream` and `.Revision` separately. 
   * If a parameterized test has completely different logic per case (if/else branches with separate AAA), split it into separate tests.

5. **Use `ITestDataSource` for integration test data.** Never hand-craft stream names with
   `$"stream-{Guid.NewGuid():N}"`. The pluggable `ITestDataSource` abstraction provides:

   - `GenerateSet(ct)` / `GenerateSet(count, ct)` — returns a `TestStream` with `.Stream`, `.Records`,
     and `.AppendRequest`
   - `GenerateManySets(count, ct)` — multiple independent streams
   - `GenerateRecord(ct)` — single-record stream

   For tests that need a stream with pre-existing data (revision mismatches, existing stream failures),
   use `SeededTestStream` which adds `.Revision` and `.Position` on top of `TestStream`.
